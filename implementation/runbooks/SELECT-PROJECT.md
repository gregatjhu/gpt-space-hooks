# Assign a project and its Space

Use one `work-checkpoint` engine. Local installation is global; an explicit per-user profile chooses the project destination. Each user gets a registry Page beneath the approved project Space. Personal coordinator checkpoints use the separate owner-only route. A repository name, folder label or Space title alone is insufficient: verify the actual Space ID, parent Page and complete native audience before binding.

## Local host setup

1. Install the reviewed package globally using the OS runbook. Keep the profile outside Git in the private checkpoint store, for example `STORE/config/project-profiles/project-user.json`. Protect the directory/file with the platform adapter. Do not copy authentication or another user's publisher identity/store.
2. Create the explicit profile using the schema in `work-checkpoint/references/project.md`. Bind the real Space ID, per-user registry Page, approved audience and one designated publisher. Recheck the existing local frozen binding before reusing a profile ID; changed audiences require reconciliation, not silent rerouting.
3. Add a small route table to your existing Codex developer instructions. Preserve other instructions. Match only the current task's supplied working-folder ancestry or its verified repository identity; do not search home or infer a project from similar names. Paths must match on directory boundaries; remote identities must match the exact owner/repository after normalizing HTTPS/SSH syntax and `.git` suffix. Forks/new repositories require explicit assignment. A task spanning multiple projects must choose its current workstream explicitly; uncertain routing retains a pending handoff.
4. Optionally append the same project fragment to a local project folder's `AGENTS.md`, preserving prior instructions. Avoid dirtying active shared repositories with personal profile paths. Repository cloud instructions use the portable fragment below instead.

Local instruction template (replace the example values with reviewed local paths; never commit this table with personal settings):

> Read the globally installed work-checkpoint skill once. For authorized Project A work, identified by this exact folder prefix or verified owner/repository, read its project guide and use `python /installed/work-checkpoint/scripts/checkpoint.py --store /private/store --profile /private/project-a-user.json`. Read the assigned registry and newest index before resuming. Record actual chat/machine, owner, repo/commit, workstream and source observation dates. Use the project audience only for sanitized project facts; do not include private attention notes or applicant details. If identity/profile/access/tools are unavailable, preserve the original prepared handoff and report the gap. Personal coordinator capture/publication remains a separate standing user authorization; prepare it separately and never copy personal coordination fields into project summaries. Keep existing schedules/nudges.

This table is agent guidance, not a filesystem-discovery service or an automatic network publisher. SessionStart provides the installed skill; actual routing and preparation must be demonstrated in fresh sessions. Existing chats need to receive the new instructions explicitly or start/resume with current configuration; editing global config does not establish that every live chat has reloaded it.

## Shared repository/cloud setup

Through the owning project's normal branch/PR workflow, copy the reviewed `work-checkpoint` directory (all three scripts and `references/project.md`) to `.agents/skills/work-checkpoint`. Append the bounded project instruction below to existing `AGENTS.md` or supported project instructions, retaining existing guidance. Do not commit a user's private profile, store, authorization, personal notes or credentials. Ignore runtime profile/store paths through the project's normal ignore policy.

> Use `.agents/skills/work-checkpoint/SKILL.md` for this project's authorized checkpoints. The approved project Space is supplied in project/task context. Read its per-user registry and newest verified index before resuming. Require an explicit assigned user profile and private store, matching the actual Space/Page/audience; never select another user's publisher profile from a list. At start, decisions, blockers, tests/deployments and handoff, prepare sanitized project facts with actual chat/machine, owner, workstream, repository/commit and observation dates. If Page tools are absent, export the original pending JSON for the designated authorized local publisher to import without re-preparing. Do not claim publication, consumption, artifact download or dispatch without separate evidence. Personal coordination is an optional separate user-authorized route. Preserve existing project safety/deployment instructions and nudges.

Project context supplies the Space/registry links and the assigned profile/store paths that actually exist in that environment. Laptop paths do not resolve in cloud tasks. A cloud producer may use its own private producer store and the reviewed publisher profile to export original pending records; only the designated publisher's one owned store claims delivery. An ephemeral producer store is not a second publisher and must not claim/retry. Check actual native Page capability before enabling direct cloud publication. Local command hooks do not run under cloud orchestration; repository skills/instructions are the loading mechanism.

For an existing session, send the exact skill path (local or repository), project label, approved registry link and profile/store invocation. Instruct it to read and confirm the route before its next checkpoint. Do not dispatch or message other sessions without authorization.

Use the [cloud-session first prompt](CLOUD-SESSION-START.md) to make this repeatable, including when the session has no staged helper. Supply only the receiving session's authorized routes; private coordinator links and profiles remain outside shared repository instructions. Require its acceptance receipt before treating that session as covered.

## Keep distribution repositories aligned

Use one source branch history and signed commits. Fetch `main` when present and the relevant default/project branches from both repositories, compare collaborator changes and reconcile before push. Merge source changes through a reviewed PR; then push only the approved named source branches to the second repository with matching commit IDs. Never mirror-push, force-push or copy operator history. Verify both branch heads and recursive source blob trees; keep default-branch selection explicit. Synchronization is a release step, not a credential-bearing hook or background job.

## Acceptance

Prove fresh local routing for each project and the default personal route separately. Then test two authorized users in one Space and a fresh cloud reader, including old observations, forks, a pending bridge and an independently downloaded artifact. Published/read/acted and upload/download remain distinct. Current source tests and a local instruction table cannot establish cloud loading or team readback.
